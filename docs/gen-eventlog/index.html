A Records Generator

  • Build the first artifact for either running example: a parent table plus a table of records linked to it by an ID column.
  • The disaster example pairs responders (parent) with incidents (records).
  • The ecology example pairs sites (parent) with observations (records).
  • Both examples share the same shape, so one lesson covers both.
  • Start by pinning the seed and importing the standard library only.
  • random.seed makes pseudo-random numbers reproducible: the “random” sequence is really a fixed, deterministic stream.
  • Run this notebook again and you get byte-for-byte the same files.
  • Reproducibility is the whole point of synthetic data; later lessons check analyses against the truth the generator encodes.

2.1 Writing rows

  • CSV is our exchange format: plain text, no database required, readable by every tool in this book.
  • A tiny helper turns a list of dictionaries into a CSV file with a header.
  • The header row records the schema, so the file is self-describing.
  • newline="" stops Windows from inserting stray blank lines.

2.2 The parent tables

  • A parent table holds the entities that records will refer to.
  • responders is the parent for the disaster example: people, each with an ID, a name, a join date, and a role.
  • sites is the parent for the ecology example: survey locations, each with an ID, a position, and a habitat.
  • Both parents use a plain integer ID as the join key.
  • The generator documents its assumptions: the coordinate ranges pin both examples to south-eastern Australia, which would otherwise be hidden magic.

2.3 The records tables

  • A records table holds many rows per parent row; the foreign key column points back at the parent.
  • incidents belongs to the disaster example: each row is one report, tagged with the responder who handled it.
  • observations is the ecology analogue: each row is one species sighting at one site.
  • observations.site_id mirrors incidents.responder_id: one foreign key column, same role in both examples.
  • Note how make_observations consults the site’s habitat to pick a plausible species; that is an assumption the generator makes explicit.

2.4 Putting it together

  • Generate the parent tables first, then the records that reference them.
  • Writing the files is just four calls to the helper.
  • CSV is portable: these four files can be opened in Polars, DuckDB, a spreadsheet, or another language without any special tooling.

2.5 Verify the join

  • Read the files back and join each records table to its parent to confirm the foreign keys line up.
  • Polars makes the two joins one-liners, and shows the shared shape clearly.
  • A left join keeps every record and attaches the matching parent row.
  • If any foreign key had no match, the parent columns would be null; a clean run shows none, so the generator is internally consistent.
  • Because the data is synthetic, we know the right answer before any analysis: the counts, ranges, and relationships above are the ground truth.
